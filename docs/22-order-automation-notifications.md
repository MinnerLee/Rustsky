# Rustsky 学习笔记 22 · 超时订单、来单和催单

## 谁负责处理无人操作的订单

管理端操作通过 HTTP 请求触发。待付款订单可能一直等不到请求，因此 Rust 服务启动时也会启动一个 Tokio 后台任务，每 60 秒处理一次超时状态。付款等待超过 15 分钟的订单会进入超时处理。已经发起微信支付的订单需要先查单，见 [第 25 篇](25-wechat-payment.md)。派送开始超过 1 小时且仍在派送的订单会完成。

两台 Rust 实例都运行这个任务。更新条件带有旧状态，例如 `WHERE status=1 AND pay_status=0`。其中一个实例把订单改为已取消后，另一个实例已经匹配不到这条记录。顾客付款和任务取消也通过数据库的更新条件决定哪个操作生效。

## WebSocket 为什么能即时推送

浏览器平时主动请求接口，服务器返回结果。WebSocket 先用 HTTP 升级连接，随后保持连接打开，服务器有消息时就能主动发给浏览器。管理端连接 `/api/order/events`，Nginx 转发 `Upgrade` 和 `Connection` 请求头，浏览器在连通后用第一条消息发送员工 JWT。服务端验证管理员身份后返回 `type: 0`。

模拟支付成功后，订单更新和 `order_event` 的来单消息一起提交。顾客对自己的待接单订单催单时，也向这张表写入一条消息。WebSocket 处理函数每秒读取新的事件，因此 Nginx 把写入和 WebSocket 交给不同 Rust 实例时，管理端依然能收到消息。来单的类型是 `1`，催单是 `2`。

催单检查会先锁住订单，再查这一分钟里是否已经提醒过。两个同时到达的催单请求依次检查，第二个能看到第一个写入的提醒。浏览器断开重连后接收之后的新消息，待处理订单仍可从订单列表查询。后台任务清理七天前的推送事件。

## 在本机验证

```powershell
& D:\rust\Rustsky\tools\test-dish.ps1 -IncludeSetmeal -IncludeCache -IncludeAutomation
```

脚本实际通过 Nginx 建立 WebSocket，验证模拟付款发出来单、顾客催单发出提醒，以及短时间重复催单被拦截。它再把自己创建的一笔未付款订单调到 20 分钟前，等待后台任务自动取消。也可以登录 [管理端](http://127.0.0.1:8888/sky/)，从 [Swagger](http://127.0.0.1:8888/docs/) 给本地测试订单模拟付款，观察管理端提示。
