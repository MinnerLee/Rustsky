# Rustsky 学习笔记 01 · 认识苍穹外卖

这篇对应课程第 4 集「Day01-03 苍穹外卖项目介绍」。课程用 Java 搭建后端，Rustsky 用 Rust 实现同一套外卖业务。本文中的 Rust 技术选型是后续开发的候选方案。

## 一个订单怎样走完流程

| 使用者 | 入口 | 主要操作 |
| --- | --- | --- |
| 餐厅员工 | Web 管理后台 | 管理员工、分类、菜品和套餐，处理订单，查看统计 |
| 顾客 | 微信小程序 | 浏览菜单、加购物车、选择地址、下单、支付和查询订单 |

以一份宫保鸡丁为例。员工在后台上架菜品，顾客在小程序看到它并加入购物车。顾客提交订单后，后端保存订单和明细。支付结果确认后，商家收到新订单提醒，继续处理订单。管理端和用户端共享同一笔订单，但权限不同。顾客只能查看自己的订单，员工根据管理权限处理店内订单。

这就是**前后端分离**的一个实际场景。前端负责页面和交互，后端通过 HTTP 接口提供数据并执行规则。举例来说，前端可以展示价格，结算时仍由后端查询价格并计算金额。

## Java 工程的分工怎样对应到 Rust

课程将后端拆成 `sky-server`、`sky-pojo` 和 `sky-common`。Rustsky 初期可以用一个 Cargo 包，通过模块组织同样的职责，等职责边界稳定后再决定是否拆包。

| 职责 | 课程做法 | Rustsky 的候选做法 |
| --- | --- | --- |
| HTTP 接口 | Spring MVC Controller | 用 Axum 的 `Router` 将请求交给 handler，由 handler 读取参数、调用业务函数并返回结果 |
| 业务逻辑 | Service | 用 Rust 函数或模块表达业务规则，例如停售菜品不能加入购物车 |
| 数据访问 | MyBatis Mapper | 用 SQLx 执行带参数的 SQL，由 MySQL 保存业务数据 |
| 请求、响应和数据行 | `sky-pojo` 中的 DTO、VO、Entity | 用不同的 `struct` 表达各自字段，用 Serde 处理 JSON |
| 通用能力 | `sky-common` | 随实际需求提取错误类型、统一响应和配置等公共模块 |

例如，员工登录时，**请求结构**需要用户名和密码，**数据库记录**需要密码哈希和账号状态，**响应结构**只需要返回前端使用的员工信息和令牌。给这三种数据分别定义结构体，可以让编译器帮我们检查字段，也减少把密码哈希带进响应的机会。

后续读代码时会遇到三个基础概念：`async` 让服务在等待数据库或网络响应时可以继续处理其他请求；`Result<T, E>` 把成功和失败写进函数签名；`mod` 组织代码并控制哪些类型和函数对其他模块可见。Tokio 提供异步运行时，Axum 负责把 HTTP 请求交给我们的代码。

## 按功能学习

| 阶段 | 先跑通的行为 | 顺带掌握的知识 |
| --- | --- | --- |
| 服务骨架 | 启动服务，访问一个健康检查接口 | Cargo 依赖、Rust 模块、Tokio、Axum 路由和 HTTP 验证 |
| 员工登录 | 正确凭证可以登录，禁用账号被拒绝 | MySQL 查询、密码哈希、JWT、身份与权限检查 |
| 菜品与套餐 | 员工上架菜品，顾客能查到菜单 | CRUD、表关系、请求校验、分页 |
| 购物车和下单 | 顾客提交订单并查询明细 | 数据库事务、金额计算、订单状态流转 |
| 通知与外部服务 | 商家收到提醒，再逐步接入微信能力 | WebSocket、Redis、支付回调与幂等 |

事务可以先用一个失败场景理解。提交订单要写订单主表和明细，并清理对应购物车。如果写明细失败，前面写入的订单也应一起回滚，顾客才能保留购物车并重试。

如果后续沿用课程前端，每个模块开工前先核对接口路径、HTTP 方法、字段名、鉴权请求头和响应格式。前端依赖的是这些接口约定，后端可以用自己的 Rust 模块组织方式。

每次开发后续模块时，学习笔记按「业务场景 → 相关知识 → Rustsky 代码示例 → 如何运行与验证」整理。当前仓库只有 Cargo 二进制骨架，尚未接入 Web 框架或数据库。
